# 0003 — Call tracing (functional)

**Date:** 2026-09-27
**Technical spec:** specs/0003-call-tracing-technical.md

## Context

An agent's work is not one LLM call but a loop: the model asks for a tool,
the agent runs it, the result goes back to the model in the next call.
The Gateway sees every call in that loop, yet treats each one as
unrelated — a call is recorded on its own, the tool calls inside it are
not recorded at all, and nothing ties the model's request for a tool to
the result the agent sends back a call later. An operator cannot answer
"what did this agent do, in what order, and how long did each step take".

Every call crosses the Gateway twice: the **request** on its way from the
agent to the LLM, and the **response** on its way back. The tool loop
spans both: the model's request for a tool arrives in a response; the
tool's result leaves in the next request. The two halves carry the same
tool-call identifier, generated by the provider. The Gateway records
each crossing separately and that identifier on both sides, so the
halves can be joined — downstream, by whatever collects the records.

Agents often know more than the Gateway about which calls belong
together. Many generate their own **session** identifier — one per
working session, spanning many user turns and sub-agents — and send it
with every call, each agent in its own place: a header, a field of the
request body, a standard tracing header. The Gateway ignores it today.

This feature observes and records. Deciding whether a tool call may run
is a separate governance step with its own spec (specs/0004).

## Goals

- Record every crossing of the Gateway: one record for each request
  (agent → the Gateway → LLM) and one for each response (LLM →
  the Gateway → agent), each written as soon as that crossing is done.
- Make the calls of one agent task linkable into a single **trace**, the
  way a distributed tracer groups the requests of one user action, using
  only identifiers the provider generated — never anything the caller
  says about which task a call belongs to.
- Keep the Gateway **stateless** between calls. Records carry both ends
  of every link they take part in, so the operator's collector can
  assemble traces, and the Gateway keeps nothing in memory from one call
  to the next. A restart, or several Gateway instances behind a load
  balancer, change nothing in the records — provided the operator sets
  the fingerprint key; with a generated key, only fingerprints differ.
- Record every tool call the model requests and every tool result the
  agent returns, with what a collector needs to join each result to the
  tool call it answers and to time it. What is recorded is metadata —
  name, identifiers, size, fingerprint, timing — never the content, so a
  record stays a few hundred bytes per tool call even when the result is a
  whole source file.
- Group calls into the agent's own session when the agent sends a
  session identifier, wherever that agent puts it. The operator
  configures where to find it, per agent, so any agent that sends one is
  supported without a change to the Gateway. A session is a label the
  agent claims and is recorded as such.
- Record what every pipeline stage decided on every request, and how
  every stage's observation of every response went, so the audit trail
  can account for every call and every decision taken on it. The Gateway
  records every crossing and hands each record to the sink; whether a
  sink delivers it is the sink's business, and a record a sink loses is
  reported, never silently (rule 23, amended by 0005).
- Describe every crossing as a record in one documented, versioned JSON
  data model, so an operator can build their own observability stack on
  it without depending on any particular tracing product. The same
  records serve both uses: **performance** (where the time goes in each
  call, stage and tool call) and **agent traces** (what the agent did, in
  what order).
- Emit records, never collect them. The Gateway hands each record, as
  soon as it is complete, to a **trace sink** that carries it downstream;
  joining, grouping, storing and querying records is the downstream
  service's job. The record does not depend on the sink, so sinks can be
  added later without changing it.
- Make records self-contained: a consumer needs nothing but the records
  to assemble a trace, and nothing from the Gateway's own logs.

## Non-goals

- Deciding whether a tool call may run. Allowing or denying tool calls —
  by tool, agent or arguments, possibly through a policy engine such as
  OPA — is a separate governance step with its own spec. This spec
  records tool calls; it never blocks, holds or alters one.
- Linking calls inside the Gateway, or keeping any state between calls.
  The Gateway assigns no trace identifier and does not check that a tool
  result answers a tool call it relayed; the collector does both from the
  records (see *Assembling a trace*).
- Recording prompt content, tool arguments or tool results. Records carry
  metadata and keyed fingerprints only; see *What the operator sees*.
- Inspecting or redacting outgoing data, including tool results, for
  leaks. That is the filtering spec's job; this spec records tool results
  but does not judge their content.
- Observing tool execution directly. The Gateway sees when a tool was
  requested and when its result came back; what happened in between, on
  the agent's side, is inferred, not observed. Tools the provider runs
  itself (server-side tools such as web search) are recorded as such.
- Linking the calls of one conversation that are not joined by a tool
  call (for example, two user turns with no tool use between them). Their
  records carry no link between them; when the agent sends a session, the
  session groups them.
- Requiring a session. A call without one is recorded like any other.
- Built-in knowledge of particular agents' session formats. The operator
  says where each agent puts its session identifier; the Gateway does not
  guess.
- Using a session for any decision. Sessions group records; they do not
  cause denials.
- Replaying a call or a task. Records are an audit trail — who called
  what, when, what was decided, how long it took — and deliberately hold
  nothing that could re-issue a call or reproduce a tool's result.
- Sending records to a downstream service over the network. A later
  spec adds network sinks; this one defines the records, the rules every
  sink follows (rules 21–24), and a single sink, **logging**.
- Exporting to OpenTelemetry. A later spec adds an OpenTelemetry sink for
  the **performance** part — call, stage, provider and tool-call timings
  — derived from the records. Agent traces stay in the JSON records only.
- Collecting, storing, assembling or querying traces. The Gateway is not
  a collection service.
- Sampling. Every crossing is recorded and handed to the sink.

## Users and scenarios

**The operator investigating an incident.** An agent deleted a directory
it should not have touched. In their observability stack, the operator
opens the agent's trace for that task — assembled by their collector from
The Gateway's records: six LLM calls in order, each with the stages that
ran on the request and what they decided, the time the provider took to
answer, and between the calls the tool calls the model requested —
`read_file`, `read_file`, `bash`, `bash` — each with its duration and
whether it reported an error. The fourth call's `bash` request is the
culprit. The operator never needed to see the prompt to find it; they can
then look up that call's fingerprint against whatever the agent logged on
its side.

**The operator following a whole session.** Agent `agent-alpha` is a
coding assistant that sends its own session identifier inside every
request body. The operator tells the Gateway where to find it for that
agent, and which part of the field is the session. From then on every
record from `agent-alpha` carries its session, and the operator's
dashboard shows a working session — several user turns, each with its
own traces, and sub-agents running in parallel under the same session —
as one unit. Agent `agent-beta` sends no session; its records carry none
and are grouped by trace only.

**The agent developer.** Nothing changes for them. Responses stream
exactly as before, and nothing they send or receive is altered.

## Behavior

### Linking calls

1. The Gateway keeps nothing between calls. A call's records are built
   from that call alone, and nothing learned from one call is remembered
   for the next. Restarting the Gateway, or spreading calls over several
   instances, produces the same records. The one exception is
   fingerprints when the operator has not set a fingerprint key: each
   running the Gateway then generates its own, so the same content gets a
   different fingerprint after a restart or on another instance. Links
   between calls never depend on fingerprints, so traces join the same
   either way.
2. The Gateway assigns no trace identifier and links no calls. The link
   between two calls is the provider's tool-call identifier, recorded in
   the first call's response record and in the second call's request
   record (rules 8 and 11); the collector joins on it (see *Assembling a
   trace*). A trace or span identifier supplied by the caller (for
   example a `traceparent` header) is ignored, never echoed, and never
   recorded. A session identifier supplied by the caller is a different
   thing: it is read only where the operator configured it (rules 14–20)
   and recorded as the caller's claim.

### Relaying responses

3. Responses are always accepted. No stage — tracing included — holds,
   alters, denies or cuts short a response: it is relayed exactly as
   without tracing, streamed chunk by chunk as the provider produces it,
   byte-identical. Stages observe responses; they never decide on them.
   This holds even when tracing fails to record part of a response (see
   *Failure behavior*).

### Records per call

4. Every call produces a **request record**, and every call whose
   request reaches the provider also produces a **response record**.
   Both carry the call's identifier, which pairs them.
5. The request record covers agent → the Gateway → LLM. It is complete
   once every stage has decided on the request, and it is handed to the
   sink **before** the request is forwarded to the provider — or, when
   the request is refused, before the refusal is sent to the agent.
6. The response record covers LLM → the Gateway → agent. It is complete
   when the response to the agent ends — its last byte relayed, the agent
   disconnected, or the provider never answered — and after every stage
   has observed the outcome. Every request that reaches the provider gets
   exactly one response record. A refused request gets none: its request
   record says what the agent received instead.
7. Both records carry the call's agent and session, so each can be
   grouped on its own, without its partner.

### Tool calls in responses

8. Every tool call the model requests in a response is recorded in the
   response record: its tool name, its identifier, whether the provider
   ran it itself, the time the Gateway relayed it, the names (not the
   values) of its arguments, the size and fingerprint of its arguments,
   and whether it reached the agent.
9. Tool calls are recorded whatever the size of the response: the limit
   on how much of a response is retained for observation does not apply
   to them. Tracing has its own, much larger **read limit** on how much
   it reads to record tool calls, so a pathological response cannot
   exhaust memory. A streamed tool call whose arguments exceed it is
   still recorded, with its name, identifier, timing and outcome, but
   with `recorded` `false` and no size, fingerprint or argument names. A
   non-streamed response that exceeds it has no tool calls read, and its
   record says so. Hitting the read limit is not a failure: the response
   is relayed unchanged and tracing's observation completes.

### Tool results in requests

10. A request resends the whole conversation, so it carries every earlier
    tool result, not only new ones. The **new** tool results are those in
    the request's last message — the ones answering the tool calls of the
    previous response. Trailing system messages do not count as the last
    message: some agents (Claude Code among them) append one after the
    message carrying the tool results. Only the new results are recorded;
    earlier ones were recorded with the call that first carried them.
11. Every new tool result is recorded in the request record: the
    identifier of the tool call it answers, whether the agent marked it
    as an error, and its size and fingerprint. The Gateway does not check
    that it relayed that tool call, or to which agent; the collector
    establishes both by joining records.

### Stage record

12. The request record lists every enabled stage's decision on the
    request: when it started, how long it took, and what it decided. A
    stage that was never asked because an earlier stage denied the
    request is recorded as not run. The response record lists every
    enabled stage that observes responses: when it started, how long it
    took, and whether its observation completed or failed. Since
    responses are always accepted (rule 3), no stage decides on them.
13. The response record is written only after every stage has observed
    the call's outcome. The audit trail receives the complete record, not
    an earlier partial one.

### Sessions

14. An operator can tell the Gateway where an agent carries its session
    identifier, as an ordered list of **sources**. A source is one of: a
    request header, by name; a field of the request body, by its path;
    or a key of the standard W3C `baggage` header. A source may add a
    pattern with exactly one capture group: only the captured part is
    then the session identifier, and a value the pattern does not match
    counts as absent.
15. A list of sources applies either to named agents or, as the default,
    to every agent without a list of its own. An agent uses its own list
    when it has one, the default otherwise, and reads no session when
    there is neither. With identification disabled, only the default
    applies.
16. Sources are tried in order; the first that yields a value gives the
    session. When none does, the call has no session. That is not an
    error: the call is forwarded and recorded as usual, and its records
    say it has no session.
17. A session identifier is valid when it is 1 to 128 characters long,
    each a printable ASCII character other than space. An invalid value
    is not recorded — not even in part — and the records mark the
    session as invalid, naming the source it came from.
18. A session belongs to the agent that sent it: sessions are told apart
    by agent and session identifier together, so two agents sending the
    same identifier have two distinct sessions. With identification
    disabled there is no agent to tell them apart by, and equal
    identifiers from different callers cannot be distinguished.
19. The session is a claim. It does not affect whether a call is allowed
    or how it is handled.
20. The Gateway reads the session and forwards the request unchanged: the
    header or field it came from reaches the provider as it would
    without the Gateway.

### Emitting records

21. The Gateway emits records; it does not collect them. Each record is
    handed to the trace sink once, on its own, as soon as it is complete
    (rules 5 and 6). The Gateway never groups records into calls or
    traces, never waits for a trace to end — it cannot know when one
    does — and keeps no record once the sink has accepted it.
22. A record is the same whatever the sink. A sink decides how records
    travel and where they go, and how they are encoded on the way; it
    never adds, drops or changes a field.
23. A sink either accepts a record or reports that it could not. A record
    the sink could not accept is **lost**: the failure is logged at error
    level, naming the call and the record, and the call is never refused,
    delayed or altered because of it (see *Failure behavior*). *Amended by
    0005: 0003 originally denied a call whose request record the sink did
    not accept.*
24. One or more sinks may be active, each receiving every record
    independently. This spec defines one kind, **logging**: it writes each
    record as one line of JSON to standard output or to a file (see
    *Logging sink*); specs/0005 adds the Cardea sink and running both.
    Sinks added by later specs consume the same records and follow rules
    21–23. *Amended by 0005: 0003 originally allowed exactly one active
    sink.*

## Operator controls

| Control | What it does | Default | At the extremes |
| --- | --- | --- | --- |
| Tracing enable | Puts tracing in the pipeline | On | Off: no records. On: every request and response is recorded |
| Session sources | Where each agent carries its session identifier, in order of preference, with an optional pattern that extracts it | None | None: no session is read, and records are grouped by trace only. Configured: records of matching calls carry the agent's session; a wrong source or pattern shows up as calls with no session or an invalid one, never as a refused call |
| Fingerprint key | The secret that keys fingerprints, read from an environment variable the operator names | None: a key is generated at startup, with a warning | None: fingerprints match only within one running the Gateway; a restart or another instance fingerprints the same content differently. Set: fingerprints match across restarts and every instance sharing the key |
| Tool-call read limit | How much of a response tracing reads to record tool calls: one streamed tool call's arguments, or a whole non-streamed response | 16 MiB | Low: large tool calls (a whole file written by an agent) are recorded without size or fingerprint. High: more memory per call in flight, only for responses that big |
| Trace sink | Which sink records are handed to, and its settings. This version offers only the logging sink, writing to standard output or to a file the Gateway appends to | Logging, to standard output | Standard output: records are separate from the application logs, which go to standard error, and are picked up by whatever collects the process's output. File: records survive in place of a log collector, and the operator rotates it |

With an operator who configures nothing, tracing is on, records go to
the logging sink on standard output, no session is read, and
fingerprints use a key generated at startup, which the Gateway warns
about. Requests
and responses pass exactly as they do today.

## Failure behavior

**Tracing fails closed on requests when tracing itself fails, never
because a sink fails, and never on responses.** A request that tracing
cannot read never reaches the provider: the operator asked for a record
of everything the agent does, and tracing that cannot do its own job is
a gap that matters in an incident. But *delivering* the record is a
different matter. *Amended by 0005:* a sink that cannot take a record
never causes a call to be refused, because a sink may depend on a remote
service or on a disk the operator does not control, and because with
several sinks one could record a call that another's failure then
refused. The loss is logged at error level and, for sinks that number
their records, visible downstream as a gap. Responses are always
accepted (rule 3): once the provider has answered, the agent receives the
response whatever tracing manages to record of it, and any gap is named
in the records and the application logs.

- **The request cannot be recorded** — its tool results cannot be read,
  or tracing errors or crashes. The call is denied with 0001's
  "governance unavailable" error naming the stage, and the provider
  never receives it.
- **A tool call in the response cannot be recorded** — tracing errors or
  crashes while reading it. The response is still relayed in full and
  unchanged. The failure is logged at error level with the call's
  identifier, and the response record shows tracing's observation as
  `failed` and the tool call with `recorded` `false`, with whatever of it
  could be recorded. This is the one gap the records can have on a call
  that was relayed, and the record names it.
- **The sink does not accept a record, request or response.** *Amended by
  0005.* The call carries on exactly as if it had: a request is forwarded
  and a response is relayed. The failure is logged at error level with
  the call's identifier and the record type, and the record is lost.
  The Gateway does not buffer records the sink refused: holding them for
  a later retry is the sink's or a collector's job, and the Cardea sink
  of 0005 does exactly that.

Handing the request record over before forwarding puts the sink's write
in every call's path. For the logging sink that is a local append; a
sink that depends on anything remote must not make the call wait on it
(specs/0005 enqueues and delivers in the background).

**Reading a session never refuses a call.** A source that is absent, a
body that does not have the expected shape, or a value that is invalid
leaves the call without a valid session, and the call proceeds and is
recorded. A session is a label the agent is free not to send; refusing a
call over it would protect nothing.

Because the Gateway keeps no state, there is no store to fill up, expire
or lose on restart, and no failure mode tied to one.

Misconfiguration — an unknown sink, a logging sink file that cannot be
opened for appending, a session source list for an agent that is not
registered or for the default given twice, a session source that names
no header, body field or baggage key, or a session pattern that is not
valid or does not have exactly one capture group, or a fingerprint key
that is set but too short — fails at startup rather than at the first
request. A fingerprint key that is not set at all is not a
misconfiguration: the Gateway generates one and warns.

## What the operator sees

Two separate outputs:

- **The records**, handed to the trace sink — a `request` record for
  every call and a `response` record for every call that reached the
  provider, described under *Trace record format* below. This is what the
  audit trail and the operator's observability stack consume.
- **The application logs**, as today, for operating the Gateway itself:
  requests and tool calls that could not be recorded, and sink failures,
  at error level, distinguishable from a deliberate denial, as in 0001.

The records are complete on their own: everything the application logs
say about a call is also in its records.

Nothing surfaced contains prompt content, tool arguments, tool results,
API keys or `Authorization` header values. Sizes and **keyed
fingerprints** stand in for arguments and results: equal contents yield
equal fingerprints within one deployment (when the operator sets the
key; with a generated key, only within one running the Gateway), so an
operator can match a tool call against the agent's own logs, but a fingerprint cannot be
reversed by guessing common values such as `ls` without the
deployment's key. Tool names and argument *names* are recorded; argument
*values* are not.

A session identifier is recorded, and only the session: when a pattern
is set, only its captured part. A body field that also carries other
identifiers — a user or an account, for example — contributes the
session and nothing else.

## Trace record format

A record is one JSON object. The format is a public contract with the
operator's stack, and the same for every sink:

- Every record carries `schema`, currently `"cardea-gateway.trace/v1"`, and
  `record`, which says its type: `request` or `response`.
- Within `v1`, record types and fields may be **added**, and fields that
  take one of a listed set of values may gain new values; nothing may be
  removed, renamed or given a different meaning. Consumers must ignore
  record types and fields they do not know, and treat values they do not
  know as opaque. Anything else is a new version.
- Timestamps are RFC 3339 in UTC with microsecond precision.
- Durations are whole microseconds, in fields ending in `_us`, so
  sub-millisecond stages stay measurable.
- A field that does not apply is `null`, never left out, and lists are
  `[]` when empty.
- Identifiers: `ak_…` per call (0001), `fp_…` for fingerprints.
  Tool-call identifiers are the provider's, unchanged.

A JSON Schema of both records is in `schemas/trace-record.v1.schema.json`.
It is the contract written out for tools; where it and this section
disagree, this section governs and the schema is fixed.

### `request` record

Agent → the Gateway → LLM. Written when every stage has decided on the
request, before it is forwarded or refused (rule 5).

```json
{
  "schema": "cardea-gateway.trace/v1",
  "record": "request",
  "call_id": "ak_7f3c2b1d9e8a4f60",
  "agent_id": "acme-bot",
  "session": {
    "id": "8d0c7a3e-5b1f-4c2a-9e6d-1f2a3b4c5d6e",
    "status": "claimed",
    "source": "body_field",
    "source_name": "metadata.user_id"
  },
  "received_at": "2026-09-27T14:03:11.402113Z",
  "duration_us": 1794,
  "model": "claude-sonnet-5",
  "stream": true,
  "size_bytes": 48213,
  "outcome": {
    "result": "forwarded",
    "status": null,
    "stage": null,
    "reason": null
  },
  "stages": [
    { "name": "identification", "started_at": "2026-09-27T14:03:11.402200Z", "duration_us": 41, "decision": "allowed", "detail": null },
    { "name": "tracing", "started_at": "2026-09-27T14:03:11.402245Z", "duration_us": 388, "decision": "allowed", "detail": null }
  ],
  "tool_results": [
    {
      "tool_call_id": "toolu_01A9",
      "is_error": false,
      "size_bytes": 5120,
      "fingerprint": "fp_9c1e0b7d44a2f316"
    }
  ],
  "findings": []
}
```

Field meanings, where the example does not make them obvious:

- `session` — always present, identical in both records of a call.
  `status` is `claimed`, `invalid` (rule 17) or `absent` (rule 16). `id`
  is set only when `claimed`. `source` is `header`, `body_field` or
  `baggage`, and `source_name` the header name, body field path or
  baggage key it came from; both are `null` when `absent`.
- `received_at`, `duration_us` — when the Gateway received the request,
  and how long it took to forward or refuse it: the Gateway's own
  overhead on the way in.
- `model` — the model the caller **requested**, as named in the request.
  `stream` — whether the caller asked for a streamed response.
- `size_bytes` — the size of the request body. `null` when the Gateway
  refused the request without reading its body in full (the body was
  too large, or could not be read).
- `outcome.result` — `forwarded`, `denied` or `failed` (a stage erred or
  crashed, or the request could not be recorded). For `denied` and
  `failed`, `status` is what the agent received, and `stage` and
  `reason` name who refused and why; `reason` is 0001's audit-only
  reason, which appears here and never in a response. For `forwarded`,
  all three are `null`: the response record says how it went.
- `stages[].decision` — `allowed`, `denied`, `failed` or `not_run`
  (rule 12). `not_run` stages have `null` timings. `stages[].detail` is
  `null` except for policies (specs/0004), which puts the policy revision
  and the identifiers of the rules that fired there.
- `tool_results[]` — the new tool results of this request (rule 10).
  `tool_call_id` is the identifier of the tool call each one answers, as
  the agent sent it; the record says nothing about whether that tool
  call exists.
- `findings[]` — objects with a `kind` and the identifiers it concerns,
  for facts visible in this request alone. None are defined yet.

### `response` record

LLM → the Gateway → agent. Written when the response to the agent ends,
for every request that reached the provider (rule 6).

```json
{
  "schema": "cardea-gateway.trace/v1",
  "record": "response",
  "call_id": "ak_7f3c2b1d9e8a4f60",
  "agent_id": "acme-bot",
  "session": {
    "id": "8d0c7a3e-5b1f-4c2a-9e6d-1f2a3b4c5d6e",
    "status": "claimed",
    "source": "body_field",
    "source_name": "metadata.user_id"
  },
  "started_at": "2026-09-27T14:03:11.403907Z",
  "first_byte_us": 620114,
  "duration_us": 4180337,
  "outcome": {
    "result": "delivered",
    "upstream_status": 200,
    "status": 200
  },
  "stages": [
    { "name": "tracing", "started_at": "2026-09-27T14:03:12.024021Z", "duration_us": 1840, "observation": "completed" }
  ],
  "streamed": true,
  "response_id": "msg_01XFDUDYJgAACzvnptvVoYEL",
  "response_model": "claude-sonnet-5-20260801",
  "stop_reason": "tool_use",
  "tokens": { "sent": 1834, "received": 212 },
  "tool_calls": [
    {
      "tool_call_id": "toolu_01B2",
      "tool_name": "bash",
      "server_side": false,
      "argument_names": ["command"],
      "size_bytes": 38,
      "fingerprint": "fp_03d8a6c2e91b7f40",
      "relayed_at": "2026-09-27T14:03:15.571930Z",
      "outcome": "delivered",
      "recorded": true
    }
  ],
  "findings": []
}
```

Field meanings, where the example does not make them obvious:

- `started_at` — when the Gateway forwarded the request to the provider.
  `first_byte_us` and `duration_us` are measured from it: time to the
  provider's first byte, and time until the response to the agent ended.
- `outcome.result` — `delivered` (the provider's response was relayed,
  whatever its status, until it ended or the agent disconnected) or
  `unanswered` (the provider never responded; the agent received a
  gateway error). There is no `denied` or `failed`: responses are always
  accepted (rule 3). `upstream_status` is the provider's HTTP status,
  `null` when `unanswered`. `status` is what the agent received: the
  provider's status when `delivered`, the Gateway's own error when
  `unanswered`.
- `stages[]` — every enabled stage that observes responses, in the order
  they observed (rule 12). `observation` is `completed`, or `failed`
  when the stage erred or crashed while observing; either way the
  response was relayed unchanged. Stages that do not observe responses
  are not listed.
- `response_id` — the provider's own identifier for the response, as
  the provider sent it, so a record can be matched against the
  provider's side (for example its usage console or a support request).
- `response_model` — the model that actually produced the response, as
  the provider reports it. It can differ from the request record's
  `model`, for example when that is an alias the provider resolves to a
  dated version.
- `stop_reason` — why the model stopped, as the provider reports it,
  unchanged (for Anthropic: `end_turn`, `tool_use`, `max_tokens`,
  `stop_sequence`, …). The Gateway does not translate it between
  providers; its meaning is the provider's.

  `response_id`, `response_model` and `stop_reason` are each `null` when
  the provider did not send them — an error response, or a stream that
  ended early.
- `tool_calls[].outcome` — `delivered`, or `not_delivered` when the
  response ended before this tool call was relayed to the agent in full:
  the agent disconnected, or the provider's stream ended early.
- `tool_calls[].recorded` — `true`, or `false` when tracing did not
  record this tool call in full: its arguments exceeded the read limit
  (rule 9), or tracing failed on it (see *Failure behavior*). Fields it
  could not read are then `null`. The tool call was relayed either way.
- `findings[]` — objects with a `kind` and the identifiers it concerns,
  for facts visible in this response alone: `response_truncated` (the
  response exceeded the observation limit; tool calls are still complete,
  rule 9), and `tool_calls_unread` (a non-streamed response exceeded the
  read limit, so its tool calls, `response_id`, `response_model`,
  `stop_reason` and `tokens` were not read, rule 9).

### Logging sink

The logging sink writes each record as JSON Lines: one record per line,
one JSON object per line, UTF-8, never pretty-printed, in the order the
records are handed to it. It writes to standard output — separate from
the application logs, which go to standard error — or appends to a file
the operator names. It adds nothing around the record: the line is the
record.

### Assembling a trace

Assembling traces is the collector's job. This section is the contract
for doing it from the records alone.

- **Call.** A `request` record and a `response` record with the same
  `call_id` are the two halves of one call. A request whose `outcome` is
  `denied` or `failed` has no response record. A forwarded request with
  no response record yet is still in flight — or its response record was
  lost (*Failure behavior*).
- **Link.** A tool call `T` in call A's `response` record and a result in
  call B's `request` record with the same `tool_call_id` link A to B:
  B continues A. Tool-call identifiers are generated by the provider and
  unique, so the link needs nothing but the two records.
- **Trace.** A trace is a set of calls connected by such links. Its
  first call is the one no link leads into.
- **Tool duration.** B's `received_at` minus `T`'s `relayed_at` in A.
  Both come from a Gateway clock; when A and B passed through
  different instances, the result is only as good as their clock
  agreement.
- **Duplicates.** A retried request can carry the same new tool result
  twice, in two request records. Keep the earliest.
- **Out of order.** Records arrive in the order they are completed, and
  calls overlap: B's request record can arrive before A's response
  record, since the agent may send B while A's record is still being
  completed. A consumer must not assume any order.

What the Gateway does not flag itself, a collector derives from the same
join:

| Finding | How to derive it |
| --- | --- |
| Unverified tool result | A tool result whose `tool_call_id` matches no tool call in any response record — a fabricated history, or a record that was lost |
| Cross-agent tool result | The two linked records have different `agent_id`s |
| Unanswered tool call | A delivered tool call with no matching result after a time the operator chooses |
| Result for an undelivered tool call | A result matching a tool call whose `outcome` was not `delivered` |
| Session mismatch | Two linked records whose `session.id` differs, or where only one has a session |

To group by session, group records by `agent_id` and `session.id`
together (rule 18). A session holds one or more traces. A record whose
`session.status` is not `claimed` belongs to no session.

## Acceptance criteria

1. **Given** the default configuration, **when** a streamed response
   containing text and a tool call is relayed, **then** the caller
   receives every chunk as the provider produces it, byte-identical to
   the same call without tracing.
2. **Given** a request that reaches the provider, **when** the call
   completes, **then** exactly one `request` record and one `response`
   record carry its `call_id`, and the request record was handed to the
   sink before the provider received the request.
3. **Given** a request denied by the second of three enabled stages,
   **when** the call completes, **then** its request record shows the
   first stage as allowed, the second as denied and the third as not
   run, with the status the agent received — and no response record is
   written.
4. **Given** a response containing a tool call, **when** the call
   completes, **then** its response record lists the tool call with its
   name, identifier, argument names, argument size and fingerprint, and
   no argument value appears in any record or in the application logs.
5. **Given** call A whose response contained tool call T, **when** call B
   arrives carrying T's result in its last message, **then** A's response
   record lists T with its `relayed_at`, B's request record lists T's
   result with the same `tool_call_id`, and joining them as described
   under *Assembling a trace* gives a duration equal to B's
   `received_at` minus T's `relayed_at`.
6. **Given** call C that resends T's result in an earlier message and has
   no tool result in its last message, **when** C is processed, **then**
   C's request record lists no tool results.
7. **Given** a request whose last message carries a tool result for an
   identifier the Gateway never relayed, **when** the call is processed,
   **then** it is forwarded normally, and its request record lists the
   result like any other, with no finding.
8. **Given** a configured fingerprint key and the Gateway restarted
   between call A and call B of criterion 5, **when** B is processed,
   **then** B's records are the same as without the restart, and A and B
   still join. **Given** no fingerprint key, **then** A and B still join,
   and B's records differ from those without the restart only in their
   fingerprints.
9. **Given** two Gateway instances, **when** call A passes through the
   first and call B through the second, **then** A and B join exactly as
   in criterion 5, whether or not the instances share a fingerprint key.
10. **Given** a caller-supplied `traceparent` header, **when** the call is
    processed, **then** the caller's value appears neither in the
    response nor in any record.
11. **Given** a sink that does not accept records, **when** a call
    arrives, **then** it is proxied normally, the agent receives the
    provider's response, and an error-level log line names the call and
    the lost request record. *(Amended by 0005; originally the call was
    denied.)*
12. **Given** a sink that stops accepting records while a call's response
    is streaming, **when** that response ends, **then** the agent has
    received the full response, the lost response record is named in an
    error-level log line, and the next call is proxied normally.
    *(Amended by 0005; originally the next call was denied.)*
13. **Given** a response larger than the maximum body size containing a
    tool call at its end, **when** the call completes, **then** the tool
    call is in its response record.
14. **Given** a provider that does not respond, **when** the call ends,
    **then** its response record has `outcome.result` `unanswered` and
    `upstream_status` `null`.
15. **Given** the default configuration, **when** calls are proxied,
    **then** standard output carries only records — one JSON object per
    line, each with `schema` `"cardea-gateway.trace/v1"`, a `record` of
    `request` or `response`, and every field of its record type present,
    `null` where it does not apply — and application log lines appear
    only on standard error.
16. **Given** three calls joined by two tool calls, **when** a consumer
    assembles them from their six records alone as described under
    *Assembling a trace*, **then** it recovers the three calls in order
    and both tool calls with their durations, whatever order the records
    were written in.
17. **Given** agent X configured with the header `X-Session-Id` as its
    session source, **when** X sends `X-Session-Id: s1`, **then** both
    records of the call carry session `s1`, `claimed`, from header
    `X-Session-Id`, and the provider receives the header unchanged.
18. **Given** agent X configured with the body field `metadata.user_id`
    and the pattern `_session_([0-9a-f-]{36})$`, **when** that field is
    `user_abc_account_def_session_<uuid>`, **then** the session is the
    UUID alone, and neither `abc` nor `def` appears in any record or in
    the application logs.
19. **Given** agent X configured with headers `A` then `B`, **when** a
    request carries both, **then** the session comes from `A`; **and
    when** it carries only `B`, **then** it comes from `B`.
20. **Given** a default source of the baggage key `session.id` and no
    list for agent Y, **when** Y sends `baggage: session.id=s9,other=x`,
    **then** the session is `s9`, from baggage `session.id`.
21. **Given** no session sources at all, **when** a call carries any
    session-looking header, **then** the records' session is `absent`,
    and the call is proxied exactly as without sessions.
22. **Given** a configured source, **when** its value is 300 characters
    long or contains a newline, **then** the call is forwarded, and the
    records' session is `invalid` with a `null` id and the source named.
23. **Given** agents X and Y both sending session `s1`, **when** their
    records are grouped as described under *Assembling a trace*,
    **then** they form two sessions, not one.
24. **Given** a session pattern that is not valid, or has two capture
    groups, **when** The Gateway starts, **then** it exits with an error
    naming the source rather than starting.
25. **Given** a request for model alias `M` that the provider answers as
    dated model `M-1`, with response identifier `R` and stop reason
    `tool_use`, **when** the call completes — streamed or not — **then**
    the request record has `model` `M`, and the response record has
    `response_model` `M-1`, `response_id` `R` and `stop_reason`
    `tool_use`.
26. **Given** a streamed response whose tool call tracing fails to record,
    **when** the response ends, **then** the caller has received the
    whole response, byte-identical to the same call without tracing; the
    response record has `outcome.result` `delivered`, tracing's
    `observation` `failed`, the tool call with `recorded` `false`, and
    `stop_reason` as the provider sent it; and the failure is logged at
    error level with the call's identifier.
27. **Given** call A whose response carried tool call T, **when** A's
    response ends, **then** A's response record is handed to the sink at
    once, without waiting for T's result.
28. **Given** a stage that errs or panics while observing a response,
    **when** the call completes, **then** the caller has received the
    whole response unchanged, and the response record has
    `outcome.result` `delivered` with that stage's `observation`
    `failed`.
29. **Given** an agent that disconnects mid-stream before a tool call is
    relayed to it, **when** the call ends, **then** the response record
    lists that tool call with `outcome` `not_delivered`.
30. **Given** a streamed tool call whose arguments exceed the read limit,
    **when** the call completes, **then** the caller receives the whole
    response unchanged, and the response record lists the tool call with
    its name, identifier and `relayed_at`, `recorded` `false`, `null`
    size, fingerprint and argument names, and tracing's `observation`
    `completed`.
31. **Given** a non-streamed response larger than the read limit, **when**
    the call completes, **then** the caller receives the whole response
    unchanged, and the response record has `tool_calls` `[]`, the finding
    `tool_calls_unread`, and tracing's `observation` `completed`.

## Relationship to 0005

specs/0005 amends this feature: rules 23 and 24, the sink part of
*Failure behavior*, acceptance criteria 11 and 12, and the open question
on network sinks are updated above (each marked *Amended by 0005*). A
sink no longer refuses calls, and more than one sink may be active. What
tracing itself does when it cannot read a request is unchanged.

## Relationship to 0001

This feature keeps 0001's observe-only responses (its rule 13 and
"Responses cannot fail closed") unchanged: responses are always accepted.
It changes two things 0001 fixes, and 0001 is amended with it:

- **Rule 10 and the observer order.** The response record must be
  written after every stage has observed the outcome (rule 13), not
  before.
- **The fixed stage order** gains a position for tracing — after
  identification, so records carry the agent.

## Open questions

- ~~How the tool-call decision spec (possibly OPA) plugs in.~~ Settled by
  specs/0004: policies decide on requests only — including the tool calls
  and tool results the conversation already carries. Responses stay
  always accepted.
- Whether a later policy needs links at request time — for example,
  denying a tool result the Gateway never relayed, or capping the tool
  calls of one task. That would bring back state between calls, and
  should be designed for several instances from the start. Decided by
  the spec for that policy.
- ~~How a network sink behaves when the downstream service is slow or
  unreachable.~~ Settled by specs/0005: a sink never refuses a call; the
  Cardea sink acknowledges a record once it is queued, delivers in the
  background from a bounded buffer, and drops (and reports) records when
  the buffer is full; more than one sink may be active. This keeps rule
  21: the buffer is bounded and lost on restart, so the Gateway still
  never becomes the place records are kept.
- How the later OpenTelemetry sink represents links between calls. It
  must stay stateless too, so it can carry tool-call identifiers on each
  record's spans, but not parent one call's span under another's;
  joining them is the collector's job. The OpenTelemetry spec must not
  require a `v2` of the records.
- Whether two calls of one conversation with no tool call between them
  should be linkable for agents that send no session, for example by
  recording a fingerprint of the resent conversation. Agents that send a
  session are already grouped by it. Deferred until traces are in use
  and the gaps are known.
