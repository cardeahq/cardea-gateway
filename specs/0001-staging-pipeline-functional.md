# 0001 — Staging pipeline (functional)

**Date:** 2026-09-13
**Technical spec:** specs/0001-staging-pipeline-technical.md

## Context

The AgentKeeper RFC (2026-09-06) describes governance as six steps run in
sequence on every call — identification, policies, monitoring, filtering,
rate-limiting, audit — each able to stop the call. Today the gateway has
no such sequence: requests are forwarded to the configured provider, with
one ad-hoc token counter wrapped around them, and nothing can refuse a
call.

The six steps are specified separately, one per feature. What is missing
first is the thing they all plug into: the **staging pipeline** — the
ordered sequence itself, its rules about who may stop a call, what the
calling agent sees when one does, and what happens when a stage is
broken. Without it, each stage would invent its own answers to those
questions, and the answers are exactly where a governance layer fails
quietly.

## Goals

- Run the governance stages in a fixed, known order on every proxied call.
- Give every stage one way to allow or deny, so denials look identical to
  the calling agent no matter which stage produced them.
- Guarantee that every call produces an outcome record — allowed or
  denied — that a later audit stage can consume.
- Let an operator turn individual stages on and off without changing
  their order.
- Behave exactly as today until a stage is given something to enforce.

## Non-goals

- The stages themselves. Identification, policies, monitoring,
  filtering, rate-limiting and audit each get their own functional and
  technical spec; this one defines only the slot they occupy.
- Modifying a request or a response. A stage may allow or deny; rewriting
  payloads (redaction, compaction) is deferred until the filtering spec,
  which will extend this contract.
- Choosing the upstream provider. Unchanged: agentkeeper decides from
  config, the caller cannot see or select it.
- Per-stage timeouts, retries, and parallel execution of stages.

## Users and scenarios

**The operator** runs agentkeeper in front of an LLM API for a fleet of
sandboxed agents. They upgrade to a build with the pipeline and change no
config: every stage is already in the path, but none has been given a
rule to enforce, so traffic behaves precisely as it did before and
nothing new appears in their logs. Later they write a rule for one stage;
from that point calls that stage refuses stop at agentkeeper, and the
operator can see in the logs which stage refused and why. When the stage
misbehaves, traffic
stops rather than silently losing governance — and the logs say which
stage is at fault, so they can disable it and restore service in one
config change.

**The agent developer** points their SDK at agentkeeper instead of the
provider. Normal calls are indistinguishable from talking to the provider
directly. When a call is refused, they get a clearly-marked agentkeeper
error naming the stage that refused and an identifier they can quote to
their operator — enough to tell "governance said no" from "the provider
is down", and not enough to map out the policy by probing.

## Behavior

1. Every request that is not `/healthz` passes through the pipeline
   before reaching the provider. `/healthz` bypasses it entirely and
   answers even when a stage would deny.
2. Stages run in one fixed order, the RFC's: identification → policies →
   monitoring → filtering → rate-limiting → audit. The order is a
   property of the build, not of configuration.
3. Configuration can only enable or disable a stage; it cannot reorder
   stages or insert one. Every stage is enabled unless the operator
   explicitly disables it, and a disabled stage behaves as if it were not
   built.
4. An enabled stage that has been given nothing to enforce allows every
   call. Being enabled puts a stage in the path; it does not by itself
   refuse anything. A stage only starts denying once the operator
   configures what it should deny, in that stage's own settings.
5. Each stage, given a call, either **allows** it or **denies** it with a
   caller-visible status and message plus an audit-only reason.
6. The first denial stops the pipeline: no later stage examines the call,
   and the provider never receives it.
7. A denial returns an agentkeeper-shaped error naming the stage that
   denied, a generic message, and a per-call identifier that also appears
   in the logs. The audit-only reason is never sent to the caller.
8. The per-call identifier is generated by agentkeeper. An identifier
   supplied by the caller is ignored, never echoed, and never used in the
   record — a caller must not be able to forge or collide the trail that
   describes it.
9. When a stage fails rather than decides — it errors, times out, or
   crashes — the call is **denied**, not forwarded. The caller gets a
   "governance unavailable" error naming the stage. A broken governance
   layer must never degrade into "allow everything", and a crashing stage
   must not take down the gateway process.
10. Every enabled stage observes the call's outcome once it completes,
    whether it was allowed, denied by another stage, or failed —
    including stages that sit after the one that denied. This is what
    lets the audit stage record every call without depending on its
    position.
11. Requests with a body larger than the configured limit are denied
    before any stage runs, because no stage can inspect what was not
    read.
12. Streaming responses keep streaming: the caller receives chunks as the
    provider produces them, with no added buffering delay. Stages observe
    the completed response afterwards.
13. Once any response byte has been sent to the caller, no stage can
    retract it. A stage that wants to block content must do so on the
    request, not the response.

## Operator controls

| Control | What it does | Default | At the extremes |
| --- | --- | --- | --- |
| Per-stage enable | Turns one stage on or off, leaving order untouched | All stages on | All off: a plain proxy, and no call can be denied whatever else is configured. All on: every stage sees every call, and each enforces whatever it has been given |
| Maximum body size | Largest request body the pipeline will read so stages can inspect it; also caps how much of a response is retained for observation | 10 MiB | Too low: legitimate large prompts are denied. Too high: memory grows with concurrent calls |

With an operator who configures nothing, every stage runs and no call is
denied — because no stage has been given anything to enforce. That is
what makes on the safe default here: the switch controls whether a stage
is *in the path*, not whether it refuses anything, so an upgrade cannot
start rejecting a customer's traffic on its own. The deliberate act that
turns a stage into a gate is writing its rule, not flipping this switch.

Defaulting on also makes the failure mode the honest one. A governance
layer whose stages ship off is a layer that silently isn't running; an
operator who writes a filtering rule should not have to discover a second
switch before it takes effect. Disabling a stage stays available as the
remedy when one misbehaves — see *Failure behavior* — and it is a visible,
explicit choice in config rather than the quiet default.

## Failure behavior

**Requests fail closed.** A stage that errors, times out or panics denies
the call with a "governance unavailable" error; the request is not
forwarded. The trade is deliberate: it costs availability, and it is the
only posture where "break the stage" is not a way to bypass the control.
The operator's remedy is to disable the offending stage — one config
change, and a visible one.

**Responses cannot fail closed.** Once bytes are on the wire the caller
has them. A failure while observing a response is logged and the call is
marked as unobserved in its outcome record; it does not retroactively
change the response.

Misconfiguration — an unknown stage name, or a body limit of zero or less
— fails at startup rather than at the first request.

## What the operator sees

- One log line per denied call: the stage that denied, its audit-only
  reason, the per-call identifier, and the status returned. Enough to
  answer "why was this refused" without reading the payload.
- One log line per stage failure, at error level, naming the stage and
  the underlying error, distinguishable from a deliberate denial.
- Allowed calls add no new log lines by default; the existing token usage
  line is unchanged.

Nothing the pipeline logs contains prompt content, response content, API
keys, or `Authorization` header values. Stage reasons are written by
stages; a reason that quotes payload content is a defect in that stage.

## Acceptance criteria

1. **Given** the default configuration — every stage enabled, none given
   a rule — **when** a request is proxied, **then** the upstream receives
   it byte-identically and the caller receives the upstream's status,
   headers and body unchanged.
2. **Given** every stage explicitly disabled, **when** a request is
   proxied, **then** the result is identical to criterion 1 and no stage
   is invoked.
3. **Given** a stage that denies with status 429, **when** a request
   arrives, **then** the caller receives 429 with an agentkeeper error
   body naming that stage and a per-call identifier, and the upstream
   receives no request.
4. **Given** two enabled stages where the first denies, **when** a
   request arrives, **then** the second stage's decision step is never
   invoked.
5. **Given** a stage that returns an error, **when** a request arrives,
   **then** the caller receives a "governance unavailable" error naming
   the stage, and the upstream receives no request.
6. **Given** a stage that panics, **when** a request arrives, **then**
   the result is identical to criterion 5 and the gateway continues
   serving subsequent requests.
7. **Given** a call denied by an early stage, **when** the call
   completes, **then** every enabled stage — including those after the
   denier — is handed the outcome exactly once, carrying the denying
   stage's name and reason.
8. **Given** a body limit of N bytes, **when** a request body exceeds N,
   **then** the call is denied before any stage runs and the upstream
   receives no request.
9. **Given** a streaming (SSE) upstream response, **when** the provider
   emits a chunk, **then** the caller receives it before the response
   completes, and stage observation runs only after the final chunk.
10. **Given** a caller-supplied per-call identifier header, **when** the
    call is processed, **then** it is ignored and a freshly generated
    identifier is used in both the response and the logs.
11. **Given** a stage that denies every call, **when** `/healthz` is
    requested, **then** it still answers 200.
12. **Given** a configured stage name that does not exist, **when**
    agentkeeper starts, **then** it exits with an error naming the
    unknown stage rather than starting.

## Open questions

- Should the per-call identifier be forwarded to the upstream provider so
  a provider-side trace can be correlated with an agentkeeper audit
  entry? Deferred to the audit spec — it decides what correlation is
  worth.
- The RFC's filtering stage redacts responses, which rule 13 of
  *Behavior* forbids in this design. Whether filtering gets an opt-in
  "buffer the response fully before sending" mode, at the cost of
  streaming, is for the filtering spec to settle.
